Test Plan

1. Objective

The objective of this test project is to evaluate the functional behavior of the SauceDemo web application and identify defects that could negatively affect the user experience.

The testing will also demonstrate manual QA practices including test case development, functional testing, negative testing, exploratory testing, defect reporting, regression testing, and test execution documentation.

2. Scope

The following application functionality will be tested:

* User authentication
* Product inventory
* Product sorting
* Product details
* Shopping cart
* Checkout information
* Order processing
* Form validation
* Navigation

3. Out of Scope

The following areas are outside the scope of this project:

* Backend source-code testing
* Database testing
* Load and performance testing
* Security penetration testing
* Automated testing
* Source-code review

4. Testing Approach

Testing will include the following approaches:

Functional Testing

Verify that application features operate according to their expected behavior.

Negative Testing

Attempt invalid inputs and unexpected user actions to determine whether the application handles them appropriately.

Smoke Testing

Perform basic tests to determine whether the application’s primary functionality is operational.

Regression Testing

Retest previously identified functionality after changes or fixes to determine whether existing functionality continues to work correctly.

Exploratory Testing

Explore the application outside of predefined test cases to identify unexpected behavior and potential defects.

UI Testing

Verify that important interface elements are displayed correctly and behave as expected.

6. Entry Criteria

Testing will begin when:

* The application is accessible.
* Test credentials are available.
* The testing scope has been defined.
* Test cases have been prepared.

7. Exit Criteria

Testing will be considered complete when:

* All planned test cases have been executed.
* Failed test cases have been investigated.
* Reproducible defects have been documented.
* Identified defects have supporting evidence where appropriate.
* Regression testing has been performed where applicable.
* A final test summary has been completed.

8. Defect Severity

Critical

A defect that prevents a major portion of the application from functioning or prevents users from completing a critical workflow.

High

A defect that significantly affects an important feature but does not completely prevent use of the application.

Medium

A defect that affects functionality but has a workaround or limited impact on the overall application.

Low

A minor defect that has limited functional impact, such as a small visual or usability issue.

9. Defect Reporting

Each reproducible defect will be documented with:

* Defect ID
* Title
* Severity
* Priority
* Environment
* Preconditions
* Steps to reproduce
* Expected result
* Actual result
* Reproducibility
* Supporting evidence
* Current status

10. Test Case Results

Each test case will be assigned one of the following results:

PASS — Actual behavior matches the expected result.

FAIL — Actual behavior does not match the expected result.

BLOCKED — Testing cannot be completed because of another issue or unavailable functionality.

NOT EXECUTED — Test has not yet been performed.

11. Testing Workflow

The testing process will follow this workflow:

Plan → Design Test Cases → Execute Tests → Identify Defects → Report Defects → Retest → Regression Test → Final Summary
